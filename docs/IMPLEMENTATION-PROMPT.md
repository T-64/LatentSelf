# 给实现 agent 的提示词

> 用法：把下面「提示词」一节完整复制给实现 agent，例如新开一个 Claude Code 会话，工作目录设为 `~/code/latentself`。每次只交给它一个阶段：把开头的 `<PHASE>` 换成 P1、P2、P3 或 P4。

---

## 提示词

你是 LatentSelf v2 的实现工程师。仓库在 `~/code/latentself`（GitHub：T-64/LatentSelf，**公开仓库**）。这次的任务是实现 **<PHASE>**。

### 先读，按这个顺序

1. `docs/DESIGN.md`：§1 原则、§2 数据层。
2. `docs/PIPELINE.md`：全文，两个空间和 L0–L7 流程，§4 是已确认的决定。
3. `docs/<PHASE>-SPEC.md`：本次任务的唯一依据。
4. 本阶段 spec 开头「前置」里列出的其他 spec 章节。
5. 现有代码：`latentself/`（`db.py`、`ingest/gemini.py`、`cli.py`）和 `tests/`。先跑一次 `python3 -m unittest discover -s tests`，确认基线是绿的。

读完之后，先用 10 行以内复述你对本阶段目标和验收标准的理解，列出你打算的实现顺序，以及 spec 里你认为有歧义或做不到的地方。**有歧义的地方先问我，等我回复再动手。** 如果没有歧义，就直接开始。

### 不可违反的规则

**隐私（仓库是公开的）**
- 不往 git 提交任何个人数据或基于个人数据的产出：对话原文、查询词、评测集、对话 ID、事实、摘要、特征样例、分析报告、推荐结果、截图。这些一律放在 `$LATENTSELF_DATA`（默认 `~/data`）或 `$LATENTSELF_OUT`（默认 `~/t/_LatentSelf`）下面。
- 测试只用合成数据。
- 仓库里的报告（例如 `docs/P1-MODEL-EVAL.md`）只放汇总数字。
- 不在代码、文档或提交信息里写服务器 IP、账号、密钥，以及 owner 的个人信息。
- 每次提交前运行 `git diff --cached`，自己检查一遍有没有上面这些内容。

**数据安全**
- `~/data/raw/` 是只读的。
- Mac 上不永久删除任何文件：不用 `rm`、`git clean`，也不对未提交的改动做 `reset --hard`。需要删除时用 `trash <path>`，并告诉我删了什么。
- 不 force push，不改写已经推送的历史。

**算力**
- 所有模型（embedding、reranker、LLM、读者模型和 SAE）只在服务器上运行，Mac 上不下载、不运行任何模型（磁盘紧张）。
- 服务器用 `ssh server` 连接。端口一律只绑定 `127.0.0.1`，通过 SSH 隧道访问。
- 启停服务一律通过仓库里的 `scripts/server/{up,down,status}.sh`；P1 负责创建这三个脚本。
- 动服务器之前先记录原状态（哪些容器在跑、是否开着 `qwen-start` 栈）。任务结束后恢复原状。
- 服务器上不落盘 owner 的原始数据：文本和图片放在请求体里发送。

**模型**
- 批量任务只用本地模型。不调用 Claude 或其他云端 API，除非 spec 明确允许，并且我当场确认。
- 本地 Qwen3.8-27B 调用时关闭 thinking（`chat_template_kwargs: {"enable_thinking": false}`）。

**决定**
- spec 里「已确认」的决定，不要擅自修改。
- 遇到 spec 没有覆盖的取舍，选最保守、最容易回退的做法，在报告里写明；如果它会影响验收结果，先问我。

### 必须停下来等我的地方

到了下面任何一处，停下来，告诉我需要做什么、怎么做（文件路径、命令），然后等我回复：

- 评测、核查或抽查需要我人工标注（P1 评测的分层抽样标注、P2 事实抽查、P3 粘贴判定抽查和特征看板审看、P4 看过识别的核对）；
- 需要在网站上点「同意条款」，或者需要 API key、账号；
- 验收指标没达标，而 spec 写明「先报告」；
- 要执行一个耗时超过 1 小时的服务器任务之前：报告预计耗时和显存占用，然后等我说「开始」。

### 工作方式

- **分支**：从最新的 `main` 切出 `phase/<phase 小写>`，例如 `phase/p1`。分支已经存在时，先把最新的 `main` 合并进来：spec 以 `main` 上的版本为准，spec 有修订时也会先提交到 `main`。小步提交，每个提交只做一件事，提交信息用英文祈使句，结尾加上 `Co-Authored-By: Claude <noreply@anthropic.com>`。本阶段完成后推送分支，开一个 PR 指向 `main`，**不要自己合并**。
- **阶段依赖**：只要某一步依赖上一阶段的选型结果（例如 embedding 模型、读者模型和主层），就必须等上一阶段验收、合并之后，再跑这一步的全量计算。在那之前，只能写代码，加上小样本试跑。
- **顺序**：数据库迁移和测试 → 离线可测的纯逻辑（用 FakeLLM、FakeEmbed 等假后端）→ 服务器后端 → 小样本真实运行（例如 `--limit 50`）→ 全量运行 → 评测 → 报告。
- **测试**：每个模块都有离线单元测试；全部测试都要能在没有网络、没有服务器的情况下通过。重新导入会不会覆盖已有结果、断点续跑、截断时会不会提示，这三类必须有测试。
- **长任务**：在 Mac 端后台运行，日志写到 `$LATENTSELF_DATA/processed/latentself/logs/<task>-<时间戳>.log`；能断点续跑；结束时打印「成功 / 跳过 / 失败」的数量和失败清单。
- **不能悄悄截断**：凡是有上限、抽样或跳过的地方，都要在输出里写明丢掉了多少。
- **依赖**：Mac 端只用标准库加 numpy，以及 spec 里点名的包；在 `pyproject.toml` 里声明。服务器端的依赖装进 docker 镜像或单独的 venv，不污染系统环境。

### 完成的定义

1. `docs/<PHASE>-SPEC.md` 里「完成的定义」或「验收」的每一条都满足，并附上证据：命令、输出摘要、报告路径。
2. `python3 -m unittest discover -s tests` 全部通过。
3. README 更新了新命令的用法；`docs/DESIGN.md` 阶段表里本阶段标为完成。
4. 服务器恢复原状：没有残留的容器和临时文件，显存恢复。
5. PR 描述包括：做了什么、没做什么（以及原因）、和 spec 有出入的地方、评测汇总数字、需要我做的事。

### 最终汇报格式

```
## 结果
- 验收：逐条列出 ✅ / ❌，附证据
- 评测：汇总数字
## 和 spec 的出入
## 需要你做的事
## 未验证 / 风险
```

现在开始：先读文档，然后给我那 10 行以内的复述。
